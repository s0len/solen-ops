# A reviewed catalogue of live actions, run by a deterministic executor

This amends ADR-0001, which bundled two commitments: that the Agent's changes must be reviewable as a diff before they reach main, and that the Agent never takes a live action on the cluster. The first is load-bearing and is preserved exactly. The second is narrowed here to what its own justification actually supports.

The evidence is the queue. Every Incident Issue open when this was written required a live cluster action to clear, and not one was resolvable by a merged diff alone: #38 and #25 needed a wedged VolSync mover Job, temp PVC and ghost VolumeSnapshot deleted; #14 needed `ceph crash archive`; #16 needed a failed Job tombstone deleted; #31 needed an etcd defragment; #37 needed a Ceph warning read and answered on its merits. Four of those six — #38, #25, #14 and #16 — are reachable by the catalogue as it ships. #31 has an entry that ships disabled because of the credential it would need, and #37 is `CephHealthWarning`, which the catalogue deliberately does not cover: `ceph_health_status == 1` is every warning Ceph can raise, and no single command is a correct answer to all of them. #13, closed a day earlier, was the same VolSync shape, and #38 was cleared by hand the evening this was written. Against the eighteen Incident Issues filed from real alerts since the Gate went live, the Fix lane has opened no pull requests at all, and a perfectly working one would have opened about two. The owner built this system to have less to fix by hand, and as it stands it cannot deliver that.

ADR-0001 justified the ban on live actions two ways. "A live action leaves no trace in git" is a property of an action nobody wrote down, not of an action whose exact command text is a file on main. "The obvious live action is sometimes wrong" — krbd blocklist fencing, the raw-OSD activation deadlock — is a property of an action a model composes in the moment, from a diagnosis it has just formed, under a turn cap. Neither objection reaches a command sequence the owner has already read, understood and merged as a diff. So the remediation moves into git as a reviewed artefact and a deterministic executor runs it: the model never composes a command, it only matches an incident to a catalogued entry, and even that matching is done by a Python script with no model in the process at all.

A Catalogued Remediation therefore lives in `kubernetes/apps/observability/alert-agent/remediations/`, one file per known failure, carrying the alertname it applies to, label matchers that narrow it, the exact argv of every command, read-only preconditions that must all pass first, a blast-radius sentence, and a maximum number of runs in a window. The Remediator executes an entry only when a human has applied its own trigger label — `ready-for-remediation`, not the Fix lane's `ready-for-agent`, because asking for a reviewable pull request is a different decision from asking for a delete — to an open Incident Issue, the alert is still firing in Alertmanager with exactly one member matching the entry, that member is one of the alerts the Gate recorded in that issue's body, an enabled entry matches, and every precondition passes; it then comments the exact commands and their real output on the issue and spends the label. It never edits a file, never opens a pull request and never closes an issue. The Agent's own identity is untouched: the Remediator has its own ServiceAccount with three write verbs on three kinds, and two ValidatingAdmissionPolicies narrow those to the object names and exec commands the shipped entries actually use.

What this genuinely gives up is honest to state. A merged diff is no longer the only way the cluster changes, so `git log` is no longer a complete account of it — the Run Ledger ConfigMap and the Incident Issue comments are where a catalogued action is recorded, and they are weaker evidence than a commit. A human reviewing a catalogue entry is reviewing a command against a failure they can only imagine, not against the cluster it will meet, which is why every entry re-proves its own diagnosis in preconditions before it runs. And a bounded, rule-based executor cannot notice that this occurrence of a known failure is not the known failure; the preconditions are the whole defence there, and the budget is what stops a wrong answer being repeated.

## Consequences

- ADR-0001's other half stands unchanged: the Agent still proposes every file change as a pull request from `agent/incident-<n>`, nothing automerges, and a Fix PR is never to be "corrected" into a commit on main.
- The Remediator ships disabled. Its `ks.yaml` reference is commented out in `kubernetes/apps/observability/kustomization.yaml`, the repo's convention for a disabled app, so nothing runs until the owner uncomments one line.
- **Resolution** in `CONTEXT.md` no longer excludes every live action; a Catalogued Remediation is one, and an improvised live action is still not.
- A failure without a catalogue entry behaves exactly as before: it becomes a Diagnosis, and a Fix PR if the owner asks for one.
- The label a human applies authorises one Alert Group, not one alertname. Alertmanager groups by `alertname` here, so one Incident Issue can cover two namespaces; the Remediator acts only on an alert the Gate wrote into that issue's body and refuses the rest.
- The one entry that would need Talos `os:admin` credentials, the etcd defragment, is shipped `enabled: false` and routed through the existing `etcd-defrag` CronJob, which already holds that credential, rather than granting it to the Remediator.
- The catalogue is only as good as its worst entry, so an entry is added the way a Runbook is: after the owner has run the sequence by hand and seen it work.
